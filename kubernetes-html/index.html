1. Kubernetes Fundamentals

Why Kubernetes exists, the declarative model, reconciliation, and cluster architecture at a glance.

What Problem Does Kubernetes Solve?

Before orchestration, teams ran containers directly on VMs with hand-rolled scripts (or Docker Swarm/Mesos) to handle placement, restarts, and scaling. This broke down at scale: no standard way to describe "what should be running," no self-healing when a host died, no consistent service discovery across hundreds of hosts, and manual rolling updates that risked outages.

Kubernetes' core insight: separate desired state (what you want) from current state (what's actually running), and run continuous, independent reconciliation loops that drive current state toward desired state — forever, self-healing any drift automatically, whether caused by a crashed process, a dead node, or a network partition.

Why Kubernetes needs the declarative model (not imperative)
An imperative system ("run container X now") has no memory of intent — if the container dies, nothing knows to recreate it unless you build that logic yourself. A declarative system stores the INTENT ("3 replicas of X should always be running") as an object in etcd; a controller compares that intent against reality every reconciliation cycle and takes corrective action. This is what gives Kubernetes self-healing "for free," and it's why almost everything in the system is modeled as objects with a spec (desired) and status (observed) field.

Key architectural rule: only the API Server talks to etcd
Every other component (scheduler, controller-manager, kubelet, kubectl) communicates EXCLUSIVELY through the API Server's REST/gRPC interface — never directly to etcd. This is what makes RBAC, admission control, and audit logging universally enforceable: there is exactly one front door.
The Reconciliation Pattern (Core Mental Model)
for {
    desired := getDesiredState()   // from etcd, via informer cache
    current := getCurrentState()   // from etcd/live cluster, via informer cache
    if !equal(desired, current) {
        reconcile(desired, current)  // take corrective action (create/update/delete)
    }
    wait(triggeredByWatchEvent || periodicResync)
}

This is level-triggered, not edge-triggered: every reconcile recomputes the FULL diff rather than reacting to individual events. A dropped watch event, a controller restart, or a missed message is automatically self-healed on the next cycle — nothing is ever "permanently lost," which is the single most important robustness property of the entire system.

Interview Questions — Fundamentals (Curated Deep-Dive)

Q1. Why is Kubernetes declarative instead of imperative, and what breaks if you try to manage it imperatively at scale?

Answer: Declarative state lets any number of independent controllers reconcile the SAME desired object without coordinating directly with each other — each just watches the object and current state. Imperative management (scripts calling `docker run`) has no persistent record of intent, so recovery from any failure requires the SAME script to re-run in the SAME order; at scale (1000s of services), this becomes an unmaintainable web of run-books. Kubernetes' declarative model means "state" IS the API — any tool (kubectl, Helm, Terraform, ArgoCD) can update the SAME object and the SAME controllers reconcile it consistently.

Follow-up: "What happens if two different actors declare conflicting desired state for the same field?" → Server-Side Apply's field-manager conflict detection (409 Conflict unless `force=true`) is the modern answer — cover this in the API Server section.

Q2. Explain "level-triggered" vs "edge-triggered" and why Kubernetes deliberately chose level-triggered reconciliation.

Answer: Edge-triggered systems react only to individual transition events (e.g. "pod deleted"). If that specific event is dropped (network blip, controller restart mid-processing), the system has no other mechanism to notice the inconsistency — it's silently wrong forever. Level-triggered systems periodically (and on every watch event) recompute the FULL diff between desired and observed state, so a missed event is invisible — the very next reconcile catches and fixes it. This is why Kubernetes controllers are robust to component restarts and network partitions without needing complex message-delivery guarantees (at-least-once is enough, exactly-once is not required).

Q3. Why does ONLY the API Server talk to etcd, and what would go wrong if the Scheduler wrote to etcd directly?

Answer: Centralizing all reads/writes through the API Server gives you one enforcement point for AuthN/AuthZ/Admission/Validation/Audit-logging/Optimistic-concurrency. If the Scheduler wrote directly to etcd, it would bypass RBAC (any compromised scheduler could write anything), bypass admission webhooks (no policy enforcement), and require every component to independently implement etcd client logic, TLS, and versioned schema handling — a maintenance and security nightmare. The API Server's watch-cache abstraction also means components don't need to understand etcd's internal Raft/MVCC model at all.

Common misconception to avoid in interviews
Kubelet does NOT talk to the Scheduler or Controller Manager directly — it only watches the API Server for Pods bound to its own node (enforced additionally by the Node authorizer). All "coordination" between control plane components happens indirectly through the shared API Server + etcd state, never peer-to-peer.
Cloud Controller Manager (CCM) — Why It Was Split Out

Originally, cloud-specific logic (AWS/Azure/GCP APIs for LoadBalancer provisioning, Node lifecycle, and Route management) lived INSIDE kube-controller-manager and kubelet — meaning every Kubernetes release had to bundle code for every cloud provider. CCM extracts this into a separate, pluggable component so core Kubernetes stays cloud-agnostic. It runs three controllers: Node controller (deletes Node objects when the cloud confirms the VM is gone), Route controller (configures cloud routes for pod CIDR reachability), and Service controller (provisions cloud LoadBalancers for type: LoadBalancer Services).

Top 10 Production Scenarios

1. Control plane upgrade causes a brief API unavailability window across all 3 replicas simultaneously

Root cause: Rolling upgrade script updated all 3 API server instances behind the LB at once instead of one at a time. Fix: stagger upgrades one replica at a time, verify health via /readyz before proceeding to the next.

2. CCM fails to clean up a cloud LoadBalancer after Service deletion, leaking cost

Root cause: Finalizer on the Service object got stuck because CCM lost connectivity to the cloud API mid-deletion. Fix: monitor CCM logs for repeated deletion errors; manually remove the orphaned cloud LB and finalizer if CCM can't recover.

3. Controller-manager leader election flapping under network partition between AZs

Root cause: Lease renewal (coordination.k8s.io Lease object) missed its deadline due to cross-AZ latency spikes, triggering unnecessary re-elections. Fix: tune --leader-elect-renew-deadline/--leader-elect-retry-period, ensure control-plane nodes have low-latency interconnect.

Interview Questions — Control Plane

Q. Walk through exactly what happens when you run `kubectl apply -f deployment.yaml`, from client to running container.

See the sequence diagram above — this is the single most commonly asked "explain the internals" question at every level from mid to staff. Structure your answer in the 4 phases: (1) client-side diffing + AuthN/AuthZ/Admission at API server, (2) etcd persistence with optimistic concurrency, (3) controller-manager creates ReplicaSet+Pods, scheduler binds pod to node, (4) kubelet pulls image via CRI and starts the container, then reports status back up the chain.

Q. Why can the Scheduler and Controller Manager run as multiple replicas even though only one is "active" at a time?

Leader election via the Lease API (coordination.k8s.io) — only the lease holder performs actual work; standbys sit idle (or serve health/metrics endpoints) ready to take over within ~15s if the leader's lease expires. This gives HA without any risk of two schedulers double-binding the same pod.

3. API Server Internals

Request lifecycle, AuthN/AuthZ/Admission, watch mechanism, and Server-Side Apply.

What Problem Does It Solve / Why K8s Needs It

The API Server is the ONLY component allowed to read/write etcd. This single choke-point is what makes security (RBAC), extensibility (admission webhooks, CRDs, aggregation layer), and consistency (optimistic concurrency via resourceVersion) possible cluster-wide. Without it, every component would need its own etcd client, its own auth logic, and there would be no single point to audit or rate-limit.

Internal Architecture — The Full Request Pipeline
graph LR A[Client: kubectl/controller/webhook] -->|HTTPS mTLS| B[Authentication] B --> C[Authorization RBAC/Node/Webhook] C --> D[Mutating Admission Webhooks] D --> E[Schema/OpenAPI Validation] E --> F[Validating Admission Webhooks] F --> G[Optimistic Concurrency Check resourceVersion] G --> H[(etcd write via Raft)] H --> I[Watch event fan-out to all watchers]

kubectl apply deployment.yaml — full internal breakdown:

  1. Client-side (kubectl): computes a 3-way strategic merge patch using the local file, the live object, and the kubectl.kubernetes.io/last-applied-configuration annotation (or Server-Side Apply field-manager tracking in modern clusters).
  2. Transport: HTTPS with mTLS; client presents a certificate or bearer token.
  3. Authentication: chain of authenticators tried until one succeeds — x509 client cert, ServiceAccount JWT, OIDC token, webhook token auth. Produces a username + group list.
  4. Authorization: Node authorizer (kubelet-only special case) → RBAC (majority of real traffic) → optional webhook authorizer (e.g. OPA). Default is implicit deny; ANY matching allow rule across all bindings grants access.
  5. Mutating admission: chain includes built-ins (NamespaceLifecycle, ServiceAccount injection, DefaultStorageClass) plus custom MutatingWebhookConfigurations (e.g. Istio sidecar injector).
  6. Schema validation: OpenAPI v3 schema check against the registered type (built-in or CRD).
  7. Validating admission: ResourceQuota, PodSecurity (enforce mode), custom ValidatingWebhookConfigurations (Gatekeeper/Kyverno policies) — runs AFTER mutation, on the FINAL object.
  8. Persistence: object serialized to protobuf internally, written to etcd with the client's supplied resourceVersion checked against etcd's current revision (409 Conflict if stale).
  9. Watch fan-out: API server's in-memory watch cache pushes the new/updated object to every watcher (Deployment controller, informers, etc.) without each watcher hitting etcd directly.
The Watch Mechanism & Informer Pattern

10,000 clients cannot each poll etcd directly — the API Server maintains ONE etcd watch per resource type internally, and fans out events to all client-side watches from an in-memory ring buffer ("watch cache"). Client-go's SharedInformer wraps this: a Reflector does List+Watch, pushes deltas into a DeltaFIFO queue, an Indexer keeps a thread-safe local cache, and a workqueue decouples "an object changed" from "processing that change" (enabling deduplication, rate-limiting, and safe concurrency).

Server-Side Apply & Field Ownership
Since 1.22 (GA), the API server tracks which "manager" (client) owns which field via managedFields. Two different controllers trying to write the SAME field trigger a 409 Conflict unless force=true — this solves the classic bug where `kubectl apply` clobbers a field the HPA is actively managing (like `spec.replicas`).
API Priority and Fairness (APF)

Prevents a single noisy client (e.g. a buggy controller doing full LIST every second) from starving critical traffic like kubelet heartbeats. PriorityLevelConfigurations define concurrency shares (system, leader-election, workload-high/low, catch-all); FlowSchemas map incoming requests to a priority level + fair queue, keyed by a distinguisher (e.g. per-user) so no single tenant can monopolize a shared priority level.

Top 10 API Server Failures

1. All kubectl commands timeout, but pods keep running fine

Root cause: etcd itself is overloaded/slow (API server is only as fast as etcd underneath). Investigation: check etcd fsync latency and leader stability first, THEN look at API server CPU/memory. Resolution: address etcd disk I/O bottleneck or reduce write volume (e.g. events churn).

2. A single misbehaving controller causes cluster-wide API latency spikes

Root cause: Controller doing full unpaginated LIST of Secrets cluster-wide on every reconcile, with no rate limiting. Resolution: enable/tune APF FlowSchemas to isolate this workload's priority level; fix the controller to use informer caches instead of direct LIST calls.

3. Admission webhook outage takes down ALL pod creation cluster-wide

Root cause: `failurePolicy: Fail` on a webhook with no `namespaceSelector` exclusion, and the webhook's own pod became unreachable (e.g., deployed in an affected namespace, chicken-and-egg). Resolution: exclude kube-system/webhook's own namespace via namespaceSelector, run multiple webhook replicas across AZs with a PDB, and consider `failurePolicy: Ignore` for non-critical webhooks.

Interview Questions — API Server

Q. Explain the difference between optimistic and pessimistic concurrency, and why Kubernetes chose optimistic exclusively.

Every object carries a resourceVersion. A client must include the version it last read when updating; if etcd's current revision differs, the write is rejected with 409 Conflict and the client must re-GET and retry (client-go's RetryOnConflict helper). There's no locking/blocking because it wouldn't scale to thousands of concurrent controllers — optimistic concurrency trades a small chance of retry for massive scalability.

Q. How does the API server handle 10,000 concurrent watch connections without hammering etcd?

ONE internal etcd watch per resource type feeds an in-memory watch cache (bounded ring buffer, size via --watch-cache-sizes); all 10,000 client watches are served from THIS cache, not from etcd directly. Bookmark events let clients cheaply resume without a full relist. If a client's resourceVersion is too old (compacted away), a 410 Gone forces a full relist — this is the only case where load hits etcd again per-client.

4. ETCD Internals

Raft consensus, leader election, quorum, WAL, snapshotting, and how Kubernetes objects map to keys.

What Problem It Solves / Why K8s Needs It

Kubernetes needs a single, strongly-consistent, crash-tolerant source of truth for ALL cluster state — every Pod, Deployment, Secret, ConfigMap, and Node object. etcd provides this via the Raft consensus protocol: a distributed log replicated across an odd number of nodes, where a write is only "committed" once a MAJORITY of nodes have durably persisted it. This gives Kubernetes crash consistency (survive N/2-1 node failures without data loss) with linearizable reads/writes.

WAL, Snapshotting & MVCC

Every write is first appended to a Write-Ahead Log (WAL) on disk (fsync'd before ACK — this is why etcd needs fast SSDs) before being applied to the in-memory/BoltDB-backed state machine. Periodically, etcd takes a snapshot of the full state machine and truncates old WAL entries to bound disk usage and speed up recovery. etcd uses MVCC (Multi-Version Concurrency Control) — every write creates a new revision (monotonically increasing, cluster-wide); Kubernetes' resourceVersion IS etcd's mod-revision. Old revisions are removed via compaction; without it, the DB grows unbounded.

Top 10 ETCD Production Issues

1. "mvcc: database space exceeded" — API server becomes read-only

Root cause: Compaction disabled/lagging; MVCC history grows unbounded until hitting the default 2GB quota. Resolution: etcdctl compact <revision> then etcdctl defrag to reclaim disk. Prevention: --auto-compaction-mode=revision --auto-compaction-retention=1000.

2. Leader election flapping causing intermittent write failures

Root cause: Slow disk fsync (>100ms) or network jitter between members causes false-positive leader-lost detection. Investigation: check etcd_disk_wal_fsync_duration_seconds and etcd_server_leader_changes_seen_total. Resolution: move etcd to dedicated fast local NVMe, isolate from noisy-neighbor CPU/network contention.

3. Defragmentation of all 3 members simultaneously causes a full outage

Root cause: Defrag blocks the member from serving requests; running it cluster-wide at once removes quorum entirely. Prevention: always defrag one member at a time, verify health before moving to the next.

Interview Questions — ETCD

Q. Your etcd cluster has 2 of 3 nodes down. What happens, and how do you recover?

No quorum (need 2, only 1 remains) → etcd rejects ALL writes; API server becomes read-only/degraded for anything requiring a fresh read or write. Q. Explain etcd MVCC and how it affects Kubernetes watches.

Every write creates a new revision; Kubernetes' resourceVersion is literally this. Watches resume by replaying the revision log from a starting point — if that revision was compacted away, the watch fails with "410 Gone: too old resource version," forcing the client to do a full relist. This is exactly why client-go's Reflector handles 410 gracefully instead of crashing.

Interview Questions — Scheduler

Q. Design scheduling for an ML training job requiring 8 GPUs placed simultaneously.

The affinity rule is checked ONLY at scheduling time. A Descheduler is needed to actively rebalance in response to label drift.

6. Controller Manager

Reconciliation loops for Deployment, ReplicaSet, Node, Endpoint, and StatefulSet controllers.

How Reconciliation Loops Work (Generic Pattern)
informer.AddEventHandler(cache.ResourceEventHandlerFuncs{
    AddFunc:    func(obj interface{}) { workqueue.Add(keyOf(obj)) },
    UpdateFunc: func(old, new interface{}) { workqueue.Add(keyOf(new)) },
    DeleteFunc: func(obj interface{}) { workqueue.Add(keyOf(obj)) },
})
// Workers pop KEYS (not objects!) and RE-FETCH from the local Indexer cache
for {
    key, _ := workqueue.Get()
    err := reconcile(key)          // idempotent!
    if err != nil { workqueue.AddRateLimited(key) } else { workqueue.Forget(key) }
    workqueue.Done(key)
}

Enqueuing the KEY instead of the object (and re-fetching fresh from the Indexer when processing) avoids acting on stale data if the queue had a backlog, and naturally deduplicates rapid successive updates to the same object into one processing pass.

Deployment Controller — RollingUpdate Math
maxSurge = ceil(replicas * maxSurge%)
maxUnavailable = floor(replicas * maxUnavailable%)
// 10 replicas, 25%/25% (defaults):
// maxSurge = 3 -> up to 13 pods total during rollout
// maxUnavailable = 2 -> at least 8 must stay Ready at all times

A broken readinessProbe on the new ReplicaSet HALTS the rollout indefinitely — new pods never become Ready, so old pods are never scaled down. This is a deliberate safety mechanism, and the classic "stuck at X% rollout" symptom.

Node Controller & Endpoint Controller

Node Controller: monitors kubelet heartbeats (Lease objects); marks a Node NotReady after missing heartbeats for --node-monitor-grace-period (default 40s), then after pod-eviction-timeout (default 5 min) begins evicting pods from the unreachable node (unless tainted with NoExecute tolerations that opt out). Endpoint/EndpointSlice Controller: watches Services + Pods, maintains the mapping of ready pod IPs behind each Service — this is exactly what kube-proxy consumes to program iptables/IPVS rules.

Interview Questions — Controller Manager

Q. What happens if controller-manager crashes mid-rollout?

Because reconciliation is level-triggered and idempotent, a new leader (via leader election) picks up EXACTLY where the desired-vs-actual comparison left off — no special "resume" logic needed. On informer resync, the new leader recomputes the full diff and continues scaling old ReplicaSet down / new ReplicaSet up until desired state matches.

Q. Why do controllers re-fetch the object from the Lister instead of using the object passed to the event handler?

The object at enqueue time can be stale by the time a worker processes it (queue backlog, or dedup collapsed multiple updates). Re-fetching from the Indexer/Lister (cheap, in-memory, no API call) ensures reconciliation always acts on the LATEST known state, preventing "lost update" bugs.

The Sync Loop & PLEG

Kubelet's SyncLoop is itself a reconciliation loop: for every pod bound to this node, compare desired PodSpec against the actual container runtime state and take corrective action (start missing containers, kill+restart per restartPolicy, run probes). The PLEG (Pod Lifecycle Event Generator) periodically polls the container runtime (via CRI) for state changes and relays them into the sync loop — this decouples potentially-slow CRI calls from the main loop's responsiveness. A slow/overloaded container runtime shows up as PLEG lag, a well-known kubelet health metric (kubelet_pleg_relist_duration_seconds).

Interview Questions — Kubelet

Q. Explain the difference between kubelet's SyncLoop and the PLEG, and why both exist.

SyncLoop is the reconciliation engine comparing desired PodSpecs to actual state and issuing corrective CRI calls. The Node object is large (capacity, conditions, images, addresses); updating it every few seconds cluster-wide at scale (5,000 nodes) generates huge etcd write volume. The lightweight Lease object (just holder identity + renewTime) is updated frequently instead, while the full Node object is only updated on genuine state changes — dramatically reducing etcd write load at scale.

8. Container Runtime

CRI, OCI, containerd, Linux namespaces, and cgroups — how a container actually gets created.

CRI (Container Runtime Interface) — Why It Exists

Before CRI, kubelet had Docker-specific code hard-baked in ("dockershim"). CRI defines a standard gRPC interface (RuntimeService + ImageService) so kubelet can talk to ANY compliant runtime (containerd, CRI-O) without runtime-specific code in kubelet itself. Dockershim was removed in 1.24 — Docker Engine itself is no longer a supported direct runtime (though containerd, which Docker itself uses under the hood, still works perfectly).

How a Container Is Actually Created
graph LR KL[Kubelet] -->|CRI gRPC: RunPodSandbox| CD[containerd] CD -->|OCI spec| RUNC[runc / OCI runtime] RUNC -->|clone with namespaces| NS[New Linux Namespaces: PID, NET, MNT, UTS, IPC] RUNC -->|cgroups v2| CG[cgroup: CPU/Mem/IO limits enforced] NS & CG --> PROC[Container process starts as PID 1 in its namespace]
  1. CRI call: kubelet asks containerd to create a pod sandbox (network namespace shared by all containers in the pod) and then individual containers within it.
  2. OCI (Open Container Initiative) spec: containerd generates an OCI runtime spec (config.json) describing the exact namespaces, mounts, capabilities, and cgroup constraints.
  3. runc (or another OCI runtime like gVisor/Kata): reads the OCI spec, calls clone() with namespace flags (CLONE_NEWPID, CLONE_NEWNET, CLONE_NEWNS, CLONE_NEWUTS, CLONE_NEWIPC) to isolate the new process.
  4. cgroups: the kernel enforces CPU shares/quota, memory limits (OOM kill on breach), and I/O throttling as configured from the Pod's resources.
Namespaces vs Cgroups — The Critical Distinction
MechanismWhat It IsolatesExample
NamespacesWHAT a process can SEE (isolation)PID namespace: container sees only its own processes as PID 1..N

Why CPU limits throttle but memory limits kill
CPU is enforced via CFS quota/period — exceeding it just means the process gets ZERO CPU time for the rest of the accounting period (throttling, not death). Memory can't be "throttled" the same way — exceeding the cgroup memory limit triggers the kernel OOM killer, an immediate SIGKILL.

Interview Questions — Container Runtime

Q. Explain the relationship between CRI, OCI, containerd, and runc.

CRI is the gRPC API kubelet uses to talk to a runtime (implemented by containerd or CRI-O). OCI is the spec for what a container IMAGE and RUNTIME SPEC must look like (portable across runtimes). containerd is a CRI-compliant daemon that manages the container lifecycle (pulling images, managing snapshots, invoking the low-level runtime). runc is the reference OCI-compliant low-level runtime that actually calls into the Linux kernel (namespaces, cgroups) to spawn the isolated process. Alternatives to runc for stronger isolation: gVisor (userspace kernel intercepting syscalls) and Kata Containers (lightweight VM per pod).

Q. Why does a pod sometimes show high CPU throttling metrics despite the node having idle CPU capacity?

CFS quota enforcement is PER-CONTAINER, not node-aware — a container hits its own hard quota within a 100ms accounting period regardless of what else is (or isn't) running on the node. Check container_cpu_cfs_throttled_periods_total vs container_cpu_cfs_periods_total ratio; if high, the fix is raising/removing that container's CPU limit, not adding nodes.

9. Networking Deep Dive

The Kubernetes networking model, CNI internals, and packet flow for every traffic pattern.

The Kubernetes Networking Model (Fundamental Rules)
  • Every Pod gets its own unique IP — no NAT needed for pod-to-pod communication within the cluster.
  • Pods on any node can communicate with pods on any other node without NAT.
  • Agents on a node (kubelet) can communicate with all pods on that node.

CNI plugins are what actually IMPLEMENT these rules — Kubernetes itself only defines the contract, not the mechanism.

Packet Flow: Pod → Pod (Same Node vs Cross Node)
graph TB subgraph Node1["Node 1"] PA[Pod A 10.244.1.5] -->|veth pair| BR1[Host network namespace] end subgraph Node2["Node 2"] BR2[Host network namespace] -->|veth pair| PB[Pod B 10.244.2.8] end BR1 -->|Routed via CNI: BGP/VXLAN/direct route| BR2

Same node: packet exits Pod A's veth, host kernel forwards directly to Pod B's veth (no CNI routing decision needed, <1ms). Cross node: packet exits to host network namespace, then routed via whatever mechanism the CNI uses — direct routing (BGP-advertised routes, Calico), overlay encapsulation (VXLAN/Geneve, adds ~50 bytes overhead, watch MTU!), or eBPF-based direct socket rewriting (Cilium).

Packet Flow: Pod → Service (ClusterIP)
sequenceDiagram participant Pod as Client Pod participant Proxy as kube-proxy (iptables/IPVS/eBPF) participant Backend as Backend Pod Pod->>Proxy: SYN to ClusterIP:Port (e.g. 10.96.0.55:80) Proxy->>Proxy: PREROUTING - KUBE-SERVICES chain matches VIP Proxy->>Proxy: DNAT to a healthy backend pod IP:Port Proxy->>Backend: Forward packet (conntrack records the flow) Backend-->>Pod: Response (conntrack auto un-NATs return path)

conntrack ensures the SAME connection always routes to the SAME backend (no per-packet re-randomization) — only NEW connections get a fresh DNAT decision.

Packet Flow: Pod → External & External → Ingress

Pod → External: if the destination isn't a cluster IP, the packet is typically SNAT'd (source rewritten to the NODE's IP) before leaving the cluster, so return traffic knows how to route back — this is why external services often see the NODE's IP, not the pod's IP, unless using an egress gateway or explicit source-IP preservation config. External → Ingress: Client → cloud LoadBalancer → NodePort (or direct pod IP for some CNI/LB combos) → Ingress Controller pod (nginx/Envoy) → matches Host/Path rule → proxies to the correct backend Service → DNAT to a pod, same as any Service call.

Interview Questions — Services & DNS

Q. Explain the complete packet flow from client to pod via ClusterIP.

DNS resolves the Service name to its ClusterIP VIP. netfilter's PREROUTING hook matches the VIP via KUBE-SERVICES chain, DNATs to a specific healthy endpoint pod IP (chosen via iptables statistic match, IPVS hash, or eBPF socket rewrite). conntrack records the flow so subsequent packets in the SAME connection route consistently to the SAME pod. Response follows the reverse path, auto-un-NAT'd by conntrack.

Q. Why does the ndots:5 default cause 5x DNS query amplification for external hostnames?

Pod resolv.conf's search path tries EVERY suffix (ns.svc.cluster.local, svc.cluster.local, cluster.local, node search domain) before the bare name, for any query with FEWER than 5 dots. An external name like `api.stripe.com` (2 dots) triggers 4 failed internal lookups before finally succeeding as an absolute name — multiplying CoreDNS load 5x for every external call. Fix: fully-qualify external names with a trailing dot, tune ndots per-pod, or deploy NodeLocal DNSCache.

RBAC Evaluation Logic

Role (namespaced) / ClusterRole (cluster-wide or reusable) define WHAT actions are allowed. RoleBinding / ClusterRoleBinding define WHO gets those permissions and at what scope. A RoleBinding CAN reference a ClusterRole to reuse common definitions (e.g., "view"/"edit"/"admin") scoped to just one namespace. Evaluation is purely ADDITIVE — gather ALL applicable bindings (direct + via group membership), union all rules, ALLOW if any rule matches, implicit DENY otherwise. There is no explicit "deny" rule in native RBAC.

Interview Questions — Security

Q. Explain ServiceAccount token projection and rotation.

Since 1.21+ (GA), pods get a `projected` volume with a `serviceAccountToken` source instead of the old long-lived Secret-mounted token. Kubelet requests short-lived (default 1hr), audience-bound, object-bound (tied to the specific Pod UID) tokens from the API server's TokenRequest API, auto-refreshing the file before expiry WITHOUT restarting the pod — drastically reducing blast radius if a token leaks.

Q. Why does Kubernetes RBAC have no explicit "deny" rule?

RBAC is a pure allow-list model — implicit deny is the default, and the ONLY way to restrict access is to not grant a permission (or use a separate policy engine like OPA Gatekeeper/Kyverno for more expressive deny logic, e.g. "deny privileged pods regardless of RBAC"). This design keeps evaluation simple (union of matching rules) at the cost of not being able to carve out exceptions within RBAC alone.

14. Autoscaling

HPA, VPA, Cluster Autoscaler, and Karpenter — internal decision-making.

HPA Decision Algorithm
desiredReplicas = ceil(currentReplicas * (currentMetricValue / desiredMetricValue))
// 4 replicas, current avg CPU=150m, target=100m
// desiredReplicas = ceil(4 * 1.5) = 6

Evaluated every 15s by default. Stabilization windows prevent flapping: scale-up is fast (default 0s delay), scale-down is slow (default 300s, using the MAX recommendation over the window) to avoid a brief dip causing premature scale-in immediately followed by scale-up again.

VPA/HPA Conflict Warning
Never target the same metric with both VPA and HPA
VPA changes per-pod resource allocation, which changes the utilization PERCENTAGE HPA measures, causing HPA to react by changing replica count, which changes per-pod load, which VPA reacts to again — oscillation, not convergence. Use VPA in recommendation-only mode alongside HPA, or have VPA manage a DIFFERENT dimension than HPA scales on.

VPC CNI & IRSA

AWS VPC CNI assigns pods real VPC IPs via secondary ENIs attached to worker nodes — enabling direct Security Group application per pod (Security Groups for Pods) but constrained by ENI/IP capacity per instance type. 19. FAANG Question Bank

Curated Senior and Staff-level questions with expected depth of answer.

Senior-Level Questions (Deep Curated Set)

1. Explain what happens end-to-end when a Node becomes unreachable.

Expected depth: kubelet stops renewing its Lease → Node controller marks Node NotReady after node-monitor-grace-period (40s default) → after pod-eviction-timeout (5 min default) pods are evicted (unless they tolerate NoExecute taints) → ReplicaSet/Deployment controllers reconcile by creating replacements elsewhere → if it was a StatefulSet pod using an exclusive volume, the multi-attach safety timeout delays rescheduling further to avoid data corruption.

2. How would you debug a service that intermittently returns 5xx errors under load?

Expected depth: Systematic elimination — check endpoint health/readiness flapping, conntrack table saturation, resource throttling (CPU CFS quota) on backend pods, uneven load distribution due to iptables randomness vs a genuinely unhealthy pod, and correlate with a distributed trace to isolate WHICH hop introduces the error.

3. Design a zero-downtime Kubernetes version upgrade strategy.

Expected depth: version skew policy (control plane at most 1 minor ahead of kubelets, upgrade control plane first), PodDisruptionBudgets to make drains safe, staged rollout (staging cluster first, one node pool/AZ at a time in prod), Pluto/kubectl-deprecations scan for removed API versions before upgrading, and acknowledging control-plane rollback is hard — the real safety net is a pre-upgrade etcd snapshot.

Staff-Level Questions (Deep Curated Set)

1. How would you design Kubernetes' scheduler to support gang scheduling natively, and why doesn't it today?

Expected depth: Discuss the scheduling framework's per-pod, independent binding cycle design and why it doesn't naturally support all-or-nothing multi-pod placement (avoiding deadlock requires reserving partial allocations, which conflicts with the framework's simplicity/performance goals at massive scale). Cover how Volcano/Kueue solve this externally via a PodGroup abstraction and admission-time queuing rather than modifying core scheduler semantics — and articulate the tradeoffs of building this INTO core Kubernetes vs keeping it a pluggable extension.

2. Design a strategy for running 10,000 Kubernetes clusters with centralized policy and observability, without a single global control plane.

Expected depth: fleet management pattern (not one mega-cluster) — a central "hub" pushing policy/config via GitOps or Config Sync/Anthos-style mechanisms, tolerant of individual cluster disconnection; federated observability (Thanos/Mimir global view without requiring live connectivity to every cluster); discuss the CAP-theorem-like tradeoffs of eventual consistency in configuration propagation at this scale, and how you'd design gradual/canary policy rollout across the fleet to limit blast radius.

3. How would you re-architect etcd's role if you were designing Kubernetes from scratch today, given lessons learned about scale limits?

Expected depth: this is an open-ended systems-design/critical-thinking question — strong answers discuss separating high-churn data (Events, Leases) into a different storage tier from low-churn critical objects (Deployments, Secrets), sharding etcd by resource type or namespace to parallelize write throughput, and the real-world precedent of large operators already doing exactly this (dedicated events etcd cluster). Bonus points for discussing why a full redesign is hard: backward compatibility, the simplicity benefit of a single consistent store, and why "just shard it" reintroduces cross-shard consistency complexity Kubernetes deliberately avoided.
