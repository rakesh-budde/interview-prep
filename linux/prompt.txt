# OUTPUT RULES

## File structure

Generate one README.md file per section. Begin every section file with:

1. A short paragraph describing what the section covers.
2. A **Subtopic Index** as a Markdown hyperlink list — one link per topic, pointing to its anchor
   within the same file. Example:
   ```markdown
   ## Subtopic Index
   - [Process States](#process-states)
   - [Virtual Memory](#virtual-memory)
   - [Page Cache](#page-cache)
   ```
   Every topic listed in the section must appear as a hyperlink here.

## Topic explanation standard

For every individual topic write a single, continuous, depth-first narrative. Do NOT use a rigid
"What / Why / How" label pattern. Instead, open with a clear statement of what the topic is,
immediately flow into the internal mechanics, kernel data structures, syscalls, algorithms, state
machines, and subsystem interactions — all as one coherent expert explanation a senior interviewer
would give to a junior engineer who asked "explain this properly."

The explanation must cover, within the prose, all of the following without separate headings for each:

- What the concept is and the problem it solves
- The detailed internal mechanism (kernel data structures such as `task_struct`, `struct inode`,
  `struct page`; syscalls; algorithms like CFS, buddy allocator, slab allocator; state machines;
  ring buffers; queue behavior — whatever is relevant)
- All kernel subsystems, userspace daemons, and tools involved and how they interact
  (e.g., systemd, udev, dbus, procfs, sysfs, cgroupfs)
- Control flow and data flow (include a Mermaid or ASCII diagram when the flow is non-trivial,
  e.g., syscall entry to kernel return, page fault handling, packet flow through the network stack)
- Key syscalls, `/proc` and `/sys` entries, kernel config options, sysctls, or flags that change behavior
- Performance implications: latency, throughput, resource cost, bottlenecks, cache effects
- Security implications: threat model, attack surface, hardening (SELinux/AppArmor, capabilities,
  seccomp, namespaces)
- Scalability implications: behavior under load, at-scale limits, what breaks first (fd limits,
  PID exhaustion, memory pressure, lock contention)
- Failure modes, symptoms, diagnosis steps, and recovery
- Production best practices
- Real-world incident or scenario that shows the concept in action

After the prose, add:

```
### Key commands
```
with the most important shell / `/proc` / `/sys` / `strace` / `perf` / `bpftrace` / `ss` / `ip` /
`systemctl` / `journalctl` commands for this topic, each annotated with what it shows and when to use it.

## Per-section closing

After all topics in a section add:

### Interview Questions

20 questions total:
- 8 conceptual/internals questions with full model answers
- 6 scenario or troubleshooting questions with reasoning walkthrough
- 6 FAANG-level deep-dive questions that require kernel source-code or syscall-level knowledge

### Hands-On Labs

3–5 practical exercises with objective, setup, tasks, and expected outcome.

### Production Incidents

2–3 real-style incident narratives with symptom, investigation, root cause, recovery, and prevention.

# STYLE REQUIREMENTS

- Write as if teaching a capable engineer, not a beginner, but do not skip foundational detail.
- Prefer dense, accurate prose over bullet points within topic explanations.
- Use ASCII or Mermaid diagrams for every non-trivial flow. Label every component.
- Include actual shell commands, config file snippets, and `strace`/`perf` output annotated on
  non-obvious lines.
- Include executable CLI examples with realistic output or inline explanation.
- Never say "this is outside the scope" or "covered elsewhere." Complete every topic in place.
- Do not generate placeholder text. Write real content.
- Where relevant, reference actual kernel source paths/functions (e.g., `kernel/sched/fair.c`,
  `mm/page_alloc.c`) to ground explanations in real internals.
